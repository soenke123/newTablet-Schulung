# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**MPS Tablet-Schulung** is a browser-based learning platform for tablet workshops at a German school. It consists of a landing page and a gamified mini-game hub ("Lernwelt") where students collect virtual creatures by completing educational games. No build process — open any `.html` file directly in a browser.

## Backend-Migration

Die Plattform ist von Frontend-only (localStorage) auf **Supabase-Backend + Vercel Functions** migriert. Referenzdokument: `PROJEKTBRIEFING.md`. Kernkonzept: Cluster (Schulungs-Kohorten mit Zeitfenster + Season) statt globalem `_rel`-Flag. Fake-Mail-Accounts auf `.fake`-TLD (kein E-Mail-Versand), Cheat-Härtung über RLS + SECURITY-DEFINER-RPCs.

**Aktueller Stand: Schritte 1–4 durch. Admin-Panel produktiv. Cluster-Starthilfe (Migration 0020) neu dazugekommen.**

Migrationen 0001–0076 liegen in `supabase/migrations/`. Schema/Seed, RLS, Session-Layer, Signup, State-Persistenz, Shop-Sync, Highscores, Cluster-Bonus, Multi-School, Blob-Spielstände und das kollaborative Board sind umgesetzt.

**Frontend-Session-Layer** (`session.js` im Repo-Root): stellt `window.supabaseClient`, `getUserSeason()`, `isLoggedIn()`, `getSessionUser()`, `waitForSession()`, `window.__accessToken` (JWT für direkte REST-Aufrufe) und ein `lernwelt:session-changed`-Event bereit. Die eigentliche Profil-Query läuft per direktem `fetch` gegen `/rest/v1/user_session`, nicht über die SDK-Query-Builder — die SDK hatte cross-tab-Lock-Probleme.

**Vercel-Functions** unter `/api/`: `signup.js` (inkl. Cluster-Bonus-Ausschüttung), `admin_reset_password.js`, `admin_delete_user.js`. Env-Vars: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `FAKE_EMAIL_DOMAIN`. Siehe `api/SETUP.md`.

**Persistenz-Schicht in `creatures.js`:**
- `_serverUnlocked`-Cache für `user_unlocked_games` beim Hub-Boot (`getUnlocked()` bleibt synchron). Guest-Fallback: localStorage.
- `loadServerState()` zieht `game_state` (inkl. `coins` pro Spiel) in denselben localStorage-Blob, den der Hub liest — DB gewinnt für DB-vorhandene Games.
- `submit_game_result`-RPC (Migration 0005) persistiert Score-Submissions inkl. Coins.
- `loadServerShop`/`syncShopStateToServer` (Migration 0011) synchronisieren den Shop-State-Blob (`nests`, `bankedCoins`, `seenCreatures`, `avatarUnlocks`, …) via `user_collectibles.key='shop_state'`.

**Blob-Spielstände (`user_game_saves`, Migration 0061):** dritter Persistenz-Weg neben `game_state` (feste Spalten) und `shop_state` (jsonb mit feldweisem Merge) — ein **opaker Blob je (User, Spiel)** für Simulationsspiele, die ihren ganzen Zustand mitschleppen. RPCs `load_game_save` / `sync_game_save` / `reset_game_save`. **Kein Merge:** zwei divergierte Simulationsstände lassen sich nicht verschmelzen, deshalb gewinnt der Server beim Laden und eine `rev`-Spalte verhindert, dass ein zweites Gerät blind darüberschreibt. `load_game_save` liefert zusätzlich `age_sec` (Serveruhr) für Offline-Aufholpässe. Erster Nutzer: Startup Story (game18), Modul `GameHub/S3 Startup Story/js/cloud.js`; die Tabelle ist bewusst generisch, „The Algorithm" könnte sie unverändert mitbenutzen.

**Startup Story = abgeleitete Hub-Integration:** game18 ist das einzige Spiel ohne Runden — es meldet nichts, sondern der Hub liest den Blob und rechnet Kreatur, Wachstum und Coins selbst aus (`syncStartupStory()` in `creatures.js`, gezeigt als Reveal-Sequenz in `script.js`). Wachstum und Coins hängen beide am Peak des laufenden Spielstands; beim Freilassen wandern die Coins nach `bankedCoins` und der Slot geht auf 0, damit ein neuer Konzern wieder verdient. Der All-Time-Peak aus `game_highscores` speist nur die Bestenliste. `standalone: true` in `GAMES_CONFIG` schaltet Nester, Backup-Tausch und Runden-Items ab; Wachstumstrank und Stein der Vollendung bleiben. Details in `GameHub/S3 Startup Story/CLAUDE.md` §10.6.

**Coin-Modell:** Client-Anzeige summiert `game_state.coins` (pro Spiel) + `shop_state.bankedCoins` + `nests[].coins` — siehe `getTotalCoins()` in `script.js`. `wallets.coins` ist redundanter Gesamtstand, wird automatisch gepflegt.

**Cluster-Starthilfe (Migration 0020):** Pro Cluster im Admin-Panel konfigurierbarer Bonus — Startcoins (→ `bankedCoins`) und Season-Spiele freischalten mit zufälligem Baby-Monster pro Slot. Rarity-Roll: 85 % Normal / 10 % Rare / 5 % Epic / 0 % Legendary. Ausschüttung via `apply_cluster_bonus`-RPC bei Signup und bei manueller Cluster-Zuweisung. Grants pro (user, cluster) idempotent, Cluster-Wechsel = additiver Bonus. Deaktivieren wirkt nur für künftige Ausschüttungen.

**Das Startmonster gewinnt (Migration 0076, 2026-08-17):** Die Starthilfe legt ihr Baby in **jedes** Spiel der Season — auch in die kollaborativen Kacheln, deren Belohnung selbst ein Monster ist. Beide Schlüpf-Zweige (`board_claim_reward`, `wc_claim_reward`) fragten bisher nur ihren eigenen Vergabe-Marker ab und schrieben dann `creature = excluded.creature`: auf der Kachel stand vor dem Schlüpfen schon ein Tier, womöglich ein Epic, und beim Phasenwechsel wurde daraus eine Schnecke. Die Regel ab 0076 gilt für beide: **liegt in `game_state` schon ein Monster, passiert beim Schlüpfen nichts** — kein Wurf, kein Ersetzen (`creature = coalesce(game_state.creature, excluded.creature)`), keine Sequenz. Der Marker wird trotzdem gesetzt, sonst fragte der 5-Sekunden-Poll das endlos erneut an. `growth` wird nur noch zurückgesetzt, wenn wirklich frisch geschlüpft ist (`case when game_state.creature is null`), sonst fiele ein vorher angewendeter Wachstumstrank weg. Alles Übrige läuft unverändert: **Reality Check wächst in Phase 2→3 genau wie bisher**, samt Münzen und Bonbons — der Wachstums-Zweig fragt nicht, welches Tier dasteht, sondern was es geleistet hat. Bei **„Warum Tablets?" entfallen die 10 Münzen**, sie hängen am Schlüpfen. Zwei Fallstricke, die dabei mitgelöst wurden: `board_claim_reward` **fällt** im Skip-Fall **in den Wachstums-Zweig durch**, statt wie sonst mit dem Schlüpf-Ergebnis zurückzukehren — beide Nachhol-Schleifen (`syncRealityCheck()`, `maybeClaimReward()` in `js/board.js`) brechen beim ersten `'none'` ab, und wer erst in Phase 3 dazukommt, verlöre sonst sein Wachstum. Und: nach einem `board_reset`/`wc_reset` schlüpft für den, der sein Monster behalten hat, im zweiten Durchlauf nichts Neues mehr — bewusst so, ein Kurs, der die Einheit wiederholt, behält sein Tier.

**`games.starter_pool text[]` (0076):** `null` = Pool der Season inklusive Rarity-Roll (Normalfall). Ist der Pool gesetzt, wird **gleichverteilt ohne Rarity-Roll** daraus gezogen — sonst fiele der Wurf in 15 % der Fälle in leere Rare-/Epic-Pools. Gesetzt nur für **`game20` = `{snail, fish}`**: die Kachel verspricht allen dasselbe (`wc_creature`), also darf sie auch kein Startmonster zeigen, das dieses Versprechen bricht. Gelesen wird über `random_baby_for_game(game_id, season)`, das `apply_cluster_bonus` **und** `wc_creature(p_board)` gemeinsam benutzen — „Schnecke oder Fisch" steht damit genau einmal im System (die alte parameterlose `wc_creature()` ist gezielt gedroppt). Merkmal am Spiel statt ID im Funktionsrumpf, dieselbe Überlegung wie bei `cluster_managed` (0072). **`game19` bekommt bewusst keinen Pool:** dort darf wie in jedem anderen Spiel etwas droppen — die Deckelung nach Beitrag (`board_creature(cap)`) greift dann nur noch beim Wachstum und nicht bei der Art, und das ist der Preis dafür, dass ein Startmonster ein vollwertiges Monster ist und kein Platzhalter.

Die Tabelle zeigt für alle User auf einmal Phase, User, Peak, Geld, Watchtime, Trend, Serverkapazität, Modelle/Metadaten, Techtree-Anteil und Dark Patterns; „Details" öffnet Farmen, laufende Deals/Kampagnen und die Trend-Aufschlüsselung. Details in `GameHub/S3 Startup Story/CLAUDE.md` §10.7.

**Reality Check (`game19`, Migrationen 0062–0067):** erste **cluster-geteilte** Kachel — die Daten gehören dem Kurs, nicht dem User, und liegen deshalb weder in `game_state` noch in `shop_state` noch in `user_game_saves`, sondern in eigenen Tabellen `board_notes` + `board_state`. Ein vom Admin moderiertes Chancen/Risiken-Board in drei Phasen (1 Sammeln · 2 Recherchieren · 3 Besprechen), sechs Kategorien, drei Typen (Chance/Risiko/Vermutung). **Migration 0063** ergänzt zwei Achsen: `topics text[]` (KI / Social Media / Gaming — Mehrfachauswahl, darf leer bleiben; Kategorie bleibt die Pflicht-Achse) und `board_likes` für Zustimmung (`board_toggle_like`, PK verhindert Doppelstimmen; der eigenen Karte kann man nicht zustimmen, zugestimmt werden darf in **jeder** Phase — das Einfrieren in Phase 3 gilt dem Inhalt, nicht dem Gespräch). Weil `board_upsert_note` dabei einen Parameter bekam, wird die alte 9-Parameter-Signatur gezielt gedroppt — `create or replace` hätte eine zweite Funktion daneben gelegt und PostgREST könnte nicht mehr wählen. Kontingent 10 Post-Its + 5 Recherchen je (User, Kurs) (Migration 0066, vorher 8 + 2 — zwei Recherchen reichten in Phase 3 nicht zum Vergleichen; die Zahl steht in `board_get` **und** `board_upsert_note`, das Frontend liest sie nur aus `me.ideas_max`/`me.facts_max`); Recherchen brauchen eine vollständige Quelle (Link · AutorIn · Veröffentlichungsdatum) — erzwungen per Tabellen-Constraint **und** RPC, angezeigt in Schul-Zitierweise (`formatSource()` in `js/board.js`). RPCs: `board_get` / `board_upsert_note` / `board_delete_note` / `board_set_phase` / `board_reset`; Tabellen haben nur SELECT-Policies, geschrieben wird ausschließlich über die RPCs. Aktualisierung per 5-Sekunden-Poll auf `board_get` mit Signatur-Diff (kein Realtime — die Admin-Sichtbarkeit hängt an einer Subquery-Policy, die Realtime laut 0038 nicht zuverlässig auswertet). Moderiert wird **in der Seite selbst**, nicht im Admin-Panel; Admins wählen dort den Kurs.

**Namensgebung (Migration 0065, 2026-08-14):** Die Kachel hieß bis dahin „Zukunftsboard" — falscher Zeitpunkt: die Einheit fragt nicht, was KI und Social Media einmal anrichten werden, sondern was sie **jetzt** mit uns machen. Heißt deshalb **Reality Check**, und die Phasentexte stehen im Präsens. Mit umbenannt wurde die zweite Kartenart: aus **„Fakt" wurde „Recherche"**, weil SuS im Netz auch Müll finden und das Wort das Urteil nicht vorwegnehmen darf — ob ein Fund trägt, klärt Phase 3. Entsprechend heißt Phase 2 „Recherchieren" statt „Belegen". **Nur die sichtbaren Texte sind umbenannt**: `game19`, der Ordner `S3 Zukunftsboard` und der Speicherwert `board_notes.kind = 'fakt'` bleiben — der kind-Wert steckt in Check-Constraints und in jedem RPC aus 0062–0064. Wer im Code `fakt` liest, meint die Recherche. Der Rest dieses Abschnitts benutzt die neuen Begriffe.

**Phasentrennung (Migration 0064):** Die Phasen sind zugleich die beiden **Fächer** des Boards — Phase 1 hält die Post-Its, Phase 2 die Recherchen, und sichtbar ist immer genau **eines** (`state.viewPhase` / `viewKind()` / `visibleNotes()` in `js/board.js`). Die Phasenleiste ist deshalb kein Schild mehr, sondern der Umschalter: goldener **Rand** = da steht der Kurs, goldene **Füllung** = das siehst du gerade, gedimmt = noch nicht freigeschaltet. Zwei getrennte Signale, weil es zwei getrennte Fragen sind. Phase 3 hat kein eigenes Fach (ein Zustand, kein Inhalt) und bleibt ein `<div>` statt eines Knopfs. Schaltet die Lehrkraft auf Phase 2, ziehen alle Tablets automatisch mit; wer neu dazukommt, landet ebenfalls beim laufenden Fach — eine eigene Wahl im `sessionStorage` (`bd_vphase`) schlägt beides. Server-Regeln dazu: **neue** Post-Its nur in Phase 1 (`p_id is null and p_kind='idee' and v_phase>=2` → `phase_locked`), bestehende bleiben in Phase 2 ausdrücklich **änderbar** — nachbessern ist etwas anderes als nachlegen. Und **Recherchen bekommen keine Zustimmung** (`fact_not_likable`): eine Recherche steht oder fällt mit ihrer Quelle, das ist keine Mehrheitsfrage. Altstimmen auf Recherchen werden nicht gelöscht, sondern nur nirgends mehr angezeigt.

**Verschlankte Kopfzeile (2026-08-15):** Über dem Board standen drei Blöcke übereinander — Kopfzeile, Phasenleiste, Auftrags-Fließtext — und darunter blieb auf einem Tablet kaum ein Streifen für die Wolke. Jetzt steht in **einer** Zeile, was dauerhaft dastehen muss: Titel · Phasen (nur Nummer + Name, `bd-phase__what`/`__count` sind weg) · Board/Tabelle. Alles andere ist einen Klick entfernt, und zwar dort, wo die Frage entsteht: **das Kontingent im Formular-Titel** („Neues Post-It 4 von 10"; für Admins ohne Zahl, für die es nicht gilt) statt als Dauerzähler `bdQuota` in der Ecke, und **der Auftrag der Phase als Modal** (`bdPhaseInfo`, Texte in `PHASE_INFO`) statt als `bdHint`-Zeile. Das Modal kommt von selbst beim Öffnen des Boards und bei **jedem** Phasenwechsel — auf allen Tablets, weil der Wechsel über den 5-Sekunden-Poll ankommt und sonst nur daran zu merken wäre, dass der Plus-Knopf anders aussieht. Ausnahme: ist gerade das Erfassungs-Formular offen, gibt es nur einen Toast — ein Fenster, das sich über eine halb getippte Karte schiebt, kostet die Karte. Nachlesen jederzeit über das **?** neben den Phasen; die Einordnung „du siehst gerade ein anderes Fach als der Kurs" steht als Fußnote im selben Modal. Der Plus-Knopf ist bei vollem Kontingent nicht mehr `disabled`, sondern blass (`bd-catadd--full`) und antwortet beim Drücken mit „Du hast alle 10 Post-Its erstellt." — ein toter Knopf beantwortet die Frage „warum geht das nicht?" nicht, ein verschwundener nimmt sie mit. Die Moderationsleiste der Admins bleibt unverändert.

**Board-Ansicht = echte Wordcloud (`layoutCloud()` in `js/board.js`):** je Kategorie eine Wolke, die Karten werden per **archimedischer Spirale mit Kollisionsprüfung** von innen nach außen gesetzt — meiste Zustimmung zuerst, also größte Karte in der Mitte. Schriftgrad aus den Likes (0.88–2.20 rem, Exponent 0.65, Bezugsgröße ist das Maximum über das ganze Board); die **Spanne selbst wächst mit dem Board** (`LIKE_SPAN_REF = 5`), sonst wäre auf einem frischen Board die erste Karte mit einer einzigen Stimme sofort doppelt so groß wie alle anderen.

**Zustimmung steht auf drei Kanälen (2026-08-15):** Größe allein log — sie ist ein *Schriftgrad*, gelesen wird aber die *Fläche*, und in die geht die Textlänge mit ein: eine lange Karte mit 2 Stimmen belegt mehr Platz als eine kurze mit 7 und zieht damit mehr Blick auf sich, als der Kurs ihr gibt. Dazu kamen deshalb zwei **flächenunabhängige** Kanäle. **Sättigung:** die Zettelfarbe wandert von blass nach satt (`STANCE_RAMP` in `board.js`, je Haltung zwei Enden für Fläche und Kante, linear gemischt, als `--cn-fill`/`--cn-line` inline an der Karte). Der **Farbton bleibt** — ein blasser grüner Zettel ist weiterhin eine Chance, Sättigung ist eine zweite Achse *innerhalb* der Zettelfarbe und keine vierte Farbe (Regel 1 der Optik). Das blasse Ende hört bewusst **vor Weiß** auf, sonst sähe ein Zettel ohne Zustimmung deaktiviert aus — oder wie eine Recherche-Karte. **Stapel:** stark getragene Karten liegen auf 1 bzw. 2 zusätzlichen Blättern (`.bd-cn--st1/--st2`), bewusst nur drei Stufen — der Stapel beantwortet „viel oder wenig", die Rangfolge leisten die beiden stufenlosen Kanäle. Gebaut über `box-shadow` und **nicht** über `::before`/`::after`: das `rotate()` der Karte macht einen Stacking-Context auf, in dem ein Pseudo-Element mit `z-index:-1` *über* der eigenen Kartenfläche landet statt dahinter. Preis des Stapels: er ragt nach rechts unten über die gemessene Karte hinaus (Schatten zählen nicht zu `offsetWidth`), deshalb `CLOUD_GAP` 10 → **17** und der Zuschnitt der Tafel in `layoutCloud` plus `SHEET_REACH_X/Y` — sonst schöbe sich ein Blatt über den Nachbarn bzw. schnitte das Fenster den Randkarten ihr unterstes Blatt ab. Die Wolke wird dadurch etwas größer und der Überblick-Maßstab kleiner. **Alle drei Kanäle hängen an einer einzigen Zahl** (`strength()`, der aus `sizeFor()` herausgezogene normierte Wert): käme die Farbe aus den rohen Likes, gäbe es Karten, die groß aber blass sind — ein Widerspruch zwischen zwei Kanälen derselben Größe ist schlimmer als ein Kanal weniger. Nebeneffekt und Absicht: die `LIKE_SPAN_REF`-Dämpfung greift damit auch für Farbe und Stapel, auf einem frischen Board bleibt die Wolke von selbst ruhig. Die drei Varianten stehen als `GameHub/S3 Zukunftsboard/showroom-likes.html` im Repo. Nur die Wolke bekommt die Kanäle — `cardHTML` gibt sie ausschließlich aus, wenn eine `strength` mitkommt, das Recherche-Raster bleibt weiß und stapellos. Gemessen wird mit `offsetWidth/offsetHeight`, weil das die Maße **vor** dem `transform` liefert; die Neigung (±2,4°, sechs Winkel) steht seit 2026-08-14 in `TILTS` im **Skript** und nicht mehr im `nth-child`, weil die Platzierung den Winkel jeder Karte kennen muss: gerechnet wird mit dem achsenparallelen Rechteck der **gedrehten** Karte (`bw = w·cos + h·sin`), gesetzt wird das ungedrehte, mittig darin. Ein pauschaler `CLOUD_GAP` reichte dafür nicht — ein 300 px breiter Zettel wird durch 2,4° gut 13 px höher, zwei davon übereinander brauchten 26 px statt der vergebenen 14, und **das war die Ursache der senkrechten Überlappungen**. Der Winkel hängt an der Karten-ID, nicht an der Position, sonst zitterte die Wolke bei jedem Poll. **Frisch gezeichnete Karten bekommen ihre Position mit abgeschaltetem `transition`** (`dataset.placed` als Marker): die Messschleife liest `offsetWidth` und erzwingt damit eine Style-Berechnung, wodurch `left: 0` aus dem Stylesheet zum Ausgangswert wird und jede Karte sonst bei **jedem** Zeichnen aus der linken oberen Ecke an ihren Platz fliegt. Die weiche Bewegung ist nur für den Fall gedacht, dass dieselben Karten neu angeordnet werden (Gerät gedreht, „neu anordnen" gedrückt). Auf der Karte steht **nur der Text** — kein Kategorie-Icon, keine Themen-Symbole, kein Name, keine Zahl; der Typ ist allein der Farbton des Zettels, und wie stark eine Aussage getragen wird, sagen Größe, Sättigung und Stapel (siehe oben). Einzige Ausnahme: ein kleiner Daumen in der Ecke, wenn man selbst zugestimmt hat — sonst wüsste niemand mehr, wo er schon zugestimmt hat, und ein zweiter Doppeltipp nähme die Zustimmung unbemerkt wieder weg. Alles Weitere (Verfasser:in, Bereich, Themen, Quelle, Zustimmungszahl, Bearbeiten/Löschen und der Zustimmen-Umschalter) steht im Detail-Overlay `bdDetail` — erreichbar aus der Wolke **und aus der Tabellenzeile**, die Liste ist eine andere Sicht auf dasselbe Board und keine Sackgasse. Die Wolke gilt nur für Post-Its; **Recherchen stehen im festen Raster** (`.bd-factgrid`, seit 0064 innerhalb der jeweiligen Kategorie statt über dem Wechsler) — eine Quellenangabe will gelesen und nicht gepackt werden, und ohne Zustimmung gäbe es auch keine Größe, die etwas erzählt. Die Tabellenspalten hängen am Fach: Post-Its zeigen 👍, Recherchen die Quelle; eine „Art"-Spalte, in der überall dasselbe steht, entfällt.

**Virtuelle Tafel + Lupe (2026-08-15):** Die Wolke wird **nicht** in der Gerätebreite gepackt, sondern auf einer virtuellen Tafel, deren Breite aus der Kartenfläche folgt (`cloudWidth()`, 380–2400 px, Wunschverhältnis H/B = 0.52, in 20-px-Stufen gerundet). Danach wird das Ganze als Bild skaliert. Drei Schichten mit je einer Aufgabe: `.bd-port` (Fenster, feste Höhe, `overflow:hidden`, fängt die Finger) › `.bd-stage` (trägt `translate`+`scale`, sonst nichts) › `.bd-cloud` (die Tafel). Grund: auf einem Handy ist ein Zettel fast so breit wie der Bildschirm — die alte Fassung klemmte Kandidaten an den Spaltenrand (`if (x<0) x=0`), dort kollidierten sie miteinander und **die Wolke fiel zur Liste zusammen**. Heute werden Kandidaten außerhalb der Tafel **verworfen** statt geklemmt, und die Tafel ist mindestens `3 × breiteste Karte` breit: die erste (größte) Karte liegt in der Mitte, daneben passt nur etwas, wenn auf jeder Seite eine ganze weitere Karte Platz hat. Nebeneffekt und Absicht: alle Geräte sehen **dieselbe** Anordnung, nur unterschiedlich weit weg — am Beamer und auf dem Tablet liegt dieselbe Karte in der Mitte. Anfangsmaßstab ist der volle Überblick (siehe „Die Wolke im Format des Feldes"); `⤢` stellt ihn wieder her. Weiter als bis zum Überblick lässt sich nicht herauszoomen. Der Ausschnitt überlebt den 5-Sekunden-Poll, solange derselbe Bereich sichtbar ist und jemand ihn **selbst** eingestellt hat (`vp.touched` / `vp.key`) — ein Poll darf niemandem die Lupe aus der Hand schlagen.

**Das Feld nimmt den Platz (2026-08-15):** Die Fensterhöhe stand vorher als Zahl im Skript — höchstens 62 % der Bildschirmhöhe — **und** schrumpfte zusätzlich auf den Inhalt; bei wenigen Zetteln blieb ein Streifen, darunter leere Seite, und beim Wischen durch die sechs Bereiche sprang die halbe Seite. Jetzt gilt: **die Tafel reicht in jeder Board-Ansicht bis an die untere Bildschirmkante, unabhängig davon, was darauf liegt** (`portHeight()`; für Wolken die Fensterhöhe, für Recherche-Raster und leeren Bereich eine Mindesthöhe an `#bdBoard`). `spaceBelow()` misst dafür, was unter der Tafel noch zur Seite gehört (Polster, Kanten, Fuß — aus den Stilwerten gerechnet statt an `document.body` gemessen, weil die Tafel eine Mindesthöhe hat und die sonst mitzählte). **Genau bis zur Kante und keinen Punkt weiter:** was darunter läge, könnte man weder sehen noch antippen, und beim Schieben im Zoom verschwände der Inhalt im unsichtbaren Teil. Dazu setzt die Board-Ansicht `body.bd-fill` und **nimmt der Seite ihren Fuß** (das Polster gehört der Liste, die weiterwächst), und auf ≤ 640 px geht die Tafel **bis an beide Bildschirmkanten** (`margin: 0 -12px`, keine Seitenkanten, keine runden Ecken) — 24 px Seitenrand sind auf einem Handy keine Zierde, sondern eine Kartenspalte. Die **Lupenknöpfe hängen an der Tafel statt im Fenster**: sie bedienen die Ansicht und sollen nicht mitwandern, wenn das Fenster beim Bereichswechsel seine Einblende-Animation fährt.

**Die Wolke im Format des Feldes (2026-08-15):** `CLOUD_ASPECT = 0.52` ist weg — gepackt wird im Seitenverhältnis des Fensters (`cloudAspect()`, 0.35–1.60, in 0,05-Stufen gerundet gegen Zittern), und dieser Wert ist zugleich das Achsenverhältnis der Spirale (`ratio`) **und** die Grundlage der Tafelbreite (`cloudWidth(items, aspect)`). Vorher kam `ratio` aus Fläche ÷ Tafelbreite², und weil die Tafel mindestens `3 × breiteste Karte` breit sein muss, war das auf schmalen Geräten immer ein flaches Band: in einem hohen Fenster lag es als Streifen in der Mitte, oben und unten Luft. Jetzt legen sich die Zettel **um die Mitte herum, waagerecht wie senkrecht**, und der Überblick wird dadurch deutlich größer (Handy: grob 0,39 → 0,59 Maßstab). Preis und bewusste Änderung gegenüber dem Stand von vorher: verschieden **geformte** Bildschirme ordnen unterschiedlich an. Was bleibt, ist das Entscheidende — die Reihenfolge ist überall dieselbe, also liegt am Beamer wie auf dem Handy dieselbe Karte in der Mitte. Passend dazu ist `CLOUD_INIT_MIN` (nie kleiner als 45 %, dafür angeschnitten) ersatzlos gestrichen: **der Anfangsmaßstab ist immer der volle Überblick** (`vp.scale = vp.fit`), heranholen kann man mit zwei Fingern. Und `clampView()` hält den Ausschnitt nur noch **im** Fenster, statt eine Wolke, die in einer Richtung hineinpasst, in dieser Richtung mittig festzunageln — das fühlte sich beim Schieben im Zoom wie eine Sperre an. Ist die Wolke größer als das Fenster, sind ihre Ränder erreichbar; ist sie kleiner, lässt sie sich frei darin herumschieben.

**Gesten im Wolken-Fenster:** **Zwei Finger** schieben und zoomen, immer, auch im Überblick — dieselbe Geste für beides (der Punkt zwischen den Fingern bleibt zwischen den Fingern). Der **eine** Finger gehört zunächst weiter dem Blättern zwischen den Bereichen; erst wer selbst aufgezogen hat (`isPanMode() = vp.touched && isZoomed()`), schiebt damit den Ausschnitt, und `⤢` bringt ihn zurück ins Blättern. Deshalb steht `touch-action: pan-y` am Fenster und wird nur im Schiebe-Modus zu `none` — sonst ließe sich die Seite auf dem Handy nicht mehr scrollen. Am Rechner: **Strg/⌘ + Rad** zoomt (ohne Zusatztaste bleibt das Rad beim Seiten-Scrollen), Ziehen schiebt. Ein Tipp direkt nach einer Schiebe-/Zoom-Bewegung wird 350 ms lang verschluckt (`vp.movedAt`), sonst öffnet der abgesetzte Finger eine Karte. Die vier Knöpfe unten rechts (`.bd-zoom`): − · ⤢ · ＋ · **⟳ „neu anordnen"**. Das ⟳ erhöht `state.shuffle`, was den Startwinkel der Spirale und die Neigungen verschiebt — die Anordnung wird **rein im Gerät** gerechnet (der Server kennt nur Text und Zustimmungen), also sieht niemand sonst etwas davon. Genau deshalb ist der Knopf harmlos und braucht keine Absicherung.

**Optik = „Whiteboard" (`css/board.css`, 2026-08-14):** Die Kachel trägt bewusst **nicht** das dunkle Fantasy-Kleid des Hubs (Cinzel/Gold auf Braun), sondern bildet nach, was sie ist: eine weiße Tafel mit feinem 28-px-Raster (`.bd-surface` am `#bdBoard`, Klasse steht im HTML — sie gehört zur Bühne, nicht zum Inhalt), darauf Klebezettel in Pastell-Grün/Rot/Gelb, fast rechtwinklig (3 px), leicht schief, mit einem weichen Schatten nach rechts unten. Schrift durchgehend Inter. Fallstrick beim Nacharbeiten: `.bd-modal p` darf **kein `color`** setzen — die Regel ist spezifischer als `.bd-error` und `.bd-help` und färbt sonst die Fehlermeldung grau statt rot. Drei durchgespielte Richtungen (Whiteboard · Studio · Materialtafel) stehen als `GameHub/S3 Zukunftsboard/showroom.html` im Repo.

**Bedienung der Wolken-Ansicht:** Ein Tipp öffnet das Detail, ein **Doppeltipp** stimmt zu (mit kurzer 👍-Rückmeldung am `<body>`, weil die Wolke sofort danach neu gezeichnet wird). Beides auf demselben Ziel geht nur mit **260 ms Wartezeit** — ein Doppeltipp beginnt nun einmal als einfacher Tipp; wo gar nicht zugestimmt werden kann (`canLike()`: eigene Karte oder Recherche), entfällt sie, dort öffnet der erste Tipp sofort. Angelegt wird über den **runden Plus-Knopf neben dem Bereichsnamen** (`bdCatAdd`): Art kommt aus dem Fach, Bereich aus dem Wechsler daneben — beides ist im Formular keine Frage mehr, sondern eine Angabe (`bdModalCat`). In der Tabellenansicht gibt es ihn nicht, dort fehlt der Bereichsbezug. Zwischen den sechs Bereichen wird **gewischt** (`touchstart`/`touchend`, passiv, nur bei > 55 px und deutlich waagerechter als senkrecht — sonst stirbt das Scrollen), alternativ über die Reiter, die Pfeile oder ←/→. Im Schiebe-Modus ist das Wischen abgeschaltet, dort gehört der Finger dem Ausschnitt (siehe „Gesten im Wolken-Fenster"). Der Wechsler (`bdCatNav`) ist `sticky`, sichtbar ist immer **nur eine** Kategorie.

**Belohnung (Migrationen 0067 + 0069 + 0076, 2026-08-16):** Reality Check ist die einzige Kachel, deren Monster an einer Handlung der **Lehrkraft** hängt statt an einer eigenen Leistung — und die einzige, deren Belohnung **serverseitig gerechnet und vergeben** wird. Bei Startup Story leitet der Hub aus dem eigenen Blob ab; das geht hier nicht, weil die Bemessungsgrundlage dem Kurs gehört (`board_notes`, `board_likes`) und der Auslöser ein Phasenwechsel ist. Zwei Momente: **Phase 1 zum ersten Mal beendet ⇒ das Ei schlüpft**, **Phase 2 zum ersten Mal beendet ⇒ das Monster wächst**. „Zum ersten Mal" braucht eine eigene Spalte — `board_state.phase_max`, monoton —, weil die Lehrkraft ausdrücklich zurückschalten darf (0062 §8) und ein Rückschritt die Belohnung weder wiederholen noch zurücknehmen darf. **Seit 0076 gilt zusätzlich: liegt schon ein Monster im Spiel (Cluster-Starthilfe), fällt das Schlüpfen aus** — siehe „Das Startmonster gewinnt" oben; das Wachsen in Phase 2→3 ist davon unberührt.

*Welches Monster:* `board_creature(cap)` mit `cap = min(10, eigene Post-Its)`. Verteilung wie `determineStartupCreature()` — 5 % Epic · 20 % Libelle · 75 % Normal —, aber **nur der Normalen-Pool wird gedeckelt**, über dieselbe Hubpunkte-Leiter wie `determineCreature()` (alle drei Seasons darin: `frosch`/`pinguin`/`raptor` aus S2, `krabbe`/`hai` aus S3). Wer wenig schreibt, bekommt ein kleineres Monster, aber nicht weniger Glück.

*Wie groß (Migration 0069, ersetzt die Regel aus 0067):* zwei Teile zu je 50 %. **Teil A — bekommene Zustimmung:** `schwelle_A = 1,5 × 10 × (alle Zustimmungen / alle Post-Its)`, `teil_A = min(1, bekommen / schwelle_A)`. Der Bruch ist die durchschnittliche Zustimmung je Karte, mal 10 (das volle Post-It-Kontingent aus 0066) ergibt das, was jemand mit ausgeschöpftem Kontingent im Schnitt bekäme; der Faktor 1,5 verlangt, deutlich darüber zu liegen. **Teil B — eigene Recherchen:** `teil_B = min(1, 0,20 × Recherchen)`, fünf Recherchen sind das Kontingent, fünf × 20 % = 100 %. Zusammen `anteil = (teil_A + teil_B) / 2`, `growth = 21 × anteil`, `coins = 30 × anteil` — beide direkt aus dem Anteil, damit sich die Rundung des einen nicht in den anderen schleppt. Die Regel wird den SuS **nirgends erklärt** — weder Sequenz noch Kachel nennen Post-Its, Recherchen oder Zustimmungen.

*Warum 0067 ersetzt wurde:* dort war `schwelle = 2 × alle Zustimmungen / alle Kursmitglieder` und gemessen wurde `gegeben + bekommen`. Weil jede Zustimmung beim Gebenden und beim Empfangenden zählt, ist `Σ(gegeben+bekommen) = 2 × alle` — die Schwelle **war** also exakt der Kursmittelwert des gemessenen Werts, die Regel damit rein relativ, obwohl sie sich absolut las. Folge 1: Like-Verteilungen sind rechtsschief, der Median liegt unter dem Mittelwert, also fiel mehr als die Hälfte des Kurses durch. Folge 2: gegebene Zustimmungen gingen ungedeckelt in den eigenen Wert **und** in die Schwelle aller anderen ein — wer sich durch alle Karten doppeltippte, maxte sich in 30 Sekunden aus und drückte dabei den Kurs. In 0069 zählen **gegebene** Zustimmungen gar nicht mehr, womit sich das umdreht: Vielklicken hebt die Schwelle für alle, dem Vielklicker selbst bringt es nichts (die eigene Karte kann man nicht liken), und für alle anderen kürzt es sich fast heraus, weil die Extra-Likes im Zähler wie im Nenner landen. `likes_given` wird weiter protokolliert, aber nicht mehr gerechnet.

*Bewusste Nebenwirkung des `× 10`:* die Schwelle unterstellt immer das volle Kontingent, nicht die eigenen Post-Its. Damit zählt die **Menge** der Post-Its in Teil A mit — und der Durchschnitt eines Kurses landet bei `(Post-Its pro Kopf) / 15`, ein Kurs mit wenig Sammelzeit also tiefer (voll ausgeschöpft 67 %, bei 5 Post-Its pro Kopf 33 %). Gewollt, nicht übersehen. Wer beide Teile ganz auslässt, wächst um 0 und bekommt nichts; die Sequenz wird dann still übergangen (`nothing`-Prüfung in `maybeClaimReward()`) — einen Sockel gibt es absichtlich nicht.

*Ausbeute:* **Bonbons = Münzen** über `add_bonbons()` — das prüft selbst, ob die Einhornkatze überhaupt noch gesammelt wird, und antwortet sonst mit `skipped`. Bewusst **nicht** über `award_game_bonbons` wie game18: das deckelt auf 10 und legt den +20-Tagesbonus drauf, der an eine Runde gebunden ist. `board_claim_reward` zieht `wallets.coins` selbst nach (sonst liefe die Rangliste bis zum nächsten `sync_game_state` auseinander).

*Wo die Sequenz läuft:* **im Board selbst**, vor dem Phasen-Modal (`maybeClaimReward()` → `runReveal()` in `js/board.js`, Overlay `#bdReveal`) — wenn die Lehrkraft weiterschaltet, schlüpft es auf allen Tablets gleichzeitig, und genau das ist der Punkt einer Kurs-Kachel. Dafür lädt die Board-Seite `creatures.js` (Bilder + Ei-SVGs). Kein Münzbank-Widget dort: die Gesamtstände stehen im `lernwelt_v3`-Blob, den die Seite bewusst nicht führt — sie zeigt nur den Zuwachs. Wer in dem Moment nicht auf der Seite war, bekommt dieselbe Sequenz beim nächsten Hub-Boot (`syncRealityCheck()` in `creatures.js` → `window.__boardReveal` → `maybeShowBoardReveal()` in `script.js`); der RPC gibt jede Stufe genau einmal aus, doppelt kann es nicht kommen. Beide Wege fassen bis zu **zwei** Stufen nach, für alle, die erst in Phase 3 dazukommen. Die Schritt-Maschine (Ei → Wachstumsstufen → Ausbeute) teilen sich beide Rückkehr-Sequenzen als `runRevealSequence(spec)`; unterschiedlich sind nur Texte und der `onCoins`-Hook.

*`board_reset` gibt die Vergabe wieder frei* — löscht `board_rewards` und setzt `phase_max = 1`, damit derselbe Kurs die Einheit erneut machen kann. Das alte Monster bleibt dabei stehen und wird erst beim nächsten Schlüpfen ersetzt; die verdienten Münzen bleiben (`coins` steht darum nicht im `do update` des `game_state`-Upserts).

**Karten der Lehrkraft (Migration 0074, 2026-08-16):** In Phase 3 hängt das Gespräch daran, dass überhaupt etwas Belastbares auf dem Board liegt — was der Kurs nicht selbst gefunden hat, wirft die Lehrkraft dazu. Dafür zwei Teile.

*Vorbereitete Recherchen* stehen als `window.BOARD_PRESETS` in `GameHub/S3 Zukunftsboard/js/presets.js` — **Datei im Repo, keine Tabelle**: sie gehören keinem Kurs und keiner Schule (Material wie die PDFs in `Dokumente/`), sie sollen im Spiel ausdrücklich **nicht** editierbar sein, und ein Textbaustein braucht weder RPC noch RLS noch Migration. Im Erfassungs-Formular sitzt neben dem Titel ein Wähler (`bdPreset`/`bdPresetMenu`), der die Maske füllt und **nicht** speichert — gespeichert wird über denselben Knopf und dieselbe RPC wie jede andere Karte, eine kaputte Vorlage wird also von `validate()` und `board_upsert_note` abgewiesen wie eine kaputte Eingabe. Gefiltert nach **Art UND Bereich**: der Bereich steht beim Anlegen ohnehin fest (er kommt vom Plus-Knopf), eine Liste über alle sechs wäre eine Liste, aus der man fünf Sechstel nicht nehmen darf. Sichtbar nur für Admins, nur beim **Anlegen** (beim Bearbeiten ersetzte eine Vorlage sonst versehentlich die Karte einer Schülerin) und nur, wenn es für diese Kartenart Vorlagen gibt — für `kind:'idee'` sind bewusst keine hinterlegt, Post-Its soll der Kurs selbst schreiben. Vorlagen, deren Text schon auf dem Board liegt, sind blass markiert (Textvergleich, keine ID: nach dem Speichern interessiert die Herkunft niemanden mehr), bleiben aber klickbar — eine gelöschte Karte will man wiederhaben können. Der aktuelle Bestand ist reiner Platzhalter-Unsinn („Fakt 1–18", google.de / wikipedia.org / tagesschau.de), durchnummeriert über alle Bereiche hinweg, damit beim Testen sofort sichtbar ist, dass die Auswahl wirklich nach Bereich filtert.

*Erkennbar* sind Lehrkraft-Karten am **Rahmen** — `board_get` liefert dazu `by_admin` je Karte (Verfasser:in, nicht Betrachter:in; das `is_admin` auf oberster Ebene bleibt, was es war). In der Wolke ein **inset**-Rahmen mit 3 px Abstand zur Kante (`.bd-cn--admin`, zwei inset-Schatten: Zettelfarbe über Anthrazit): innen, weil ein äußerer Ring dem Stapel die Blätter anschnitte — ausgerechnet die stark getragenen Karten sähen aus wie ein Fehler —, und mit Abstand, weil dieselbe Linie direkt an der Kante nur nach „fetterer Rand" aussieht statt nach Absicht. Anthrazit, keine vierte Zettelfarbe (Regel 1 der Optik): der Rahmen sagt „kommt nicht aus dem Kurs", nicht „ist wichtiger". Im Recherche-Raster stattdessen anthrazitfarbene Kante plus zweite Linie (ein inset-Rahmen liefe dort unter der blauen Kopfkante des `::before` durch); die Regel steht **nach** `.bd-cn--mine`, weil eine Karte für den Admin selbst beides ist und „von der Lehrkraft" die nützlichere Auskunft ist. Dazu ein 🛡️ in der „Von"-Spalte der Tabelle und eine Lehrkraft-Pille im Detail — der Rahmen allein sagt „anders", nicht „von wem".

*Und sie zählen nicht mit:* `board_claim_reward` misst Teil A an `1,5 × 10 × (alle Zustimmungen / alle Post-Its)`, und beides lief über **sämtliche** Karten des Kurses. Eine Lehrkraft-Karte mit viel Zustimmung höbe damit die Schwelle für die ganze Klasse, ohne dass sie jemandem gutgeschrieben würde (Admins holen keine Belohnung ab); eine ohne senkte sie. Seit 0074 sind Karten von Admins aus **Zähler und Nenner** draußen — dieselbe Bedingung, mit der 0069 schon die Mitgliederzahl bereinigt. **Zustimmen** darf man ihnen weiter: das ist Teil des Gesprächs, es zählt nur nirgends mit.

**`collab`-Flag in `GAMES_CONFIG`:** dritter Kachel-Sonderfall neben `standalone` und `clusterLegi`. Gemeinsam mit `standalone` unter dem Prädikat `isRoundless(game)` in `script.js` zusammengefasst — beide melden kein Rundenergebnis, also sind Nest-Eier, Runden-Items, Backup-Tausch und Rundenbonus aus. Zusätzlich collab-spezifisch: kein Bonbon-Tages-Hinweis (die +20 hängen an einer gespielten Runde — die Bonbons kommen hier einmalig aus 0067), **kein Freilassen** (Knopf aus in `buildCardHTML`, Riegel in `confirmRelease` **und** `releaseCreature` — der Auslöser ist ein einmaliger Phasenwechsel und lässt sich nicht nachspielen), und Admins dürfen das Season-Gate passieren (`isAdminUser()` in `getGameAccess` **und** in der Season-Sektions-Filterung von `renderHub` — beide Stellen sind nötig). Wachstumstrank und Stein der Vollendung wirken wie bei `standalone`. Träger des Flags: `game19` (Reality Check, S3) und `game20` (Warum Tablets?, S1). Weil `collab` die Season-Sektion für Admins mit aufschließt, sieht die Lehrkraft seit `game20` auch die Season-1-Sektion — genau dort steht ihre Kachel.

**Kurs-Freischaltung statt Passwörter (Migrationen 0070 + 0071, 2026-08-16):** Die Spiel-Passwörter sind weg. Ein Passwort war ein **Geheimnis pro Spiel** — einmal angesagt, nicht mehr zurückzunehmen, und es wanderte in den nächsten Kurs. Gebraucht wurde das Gegenteil: ein **Schalter pro (Kurs, Spiel)**, den Admins und Schuladmins in beide Richtungen bedienen. Tabelle `cluster_unlocked_games`, bewusst parallel zu `user_unlocked_games` gebaut: **Zeile vorhanden = offen**, Sperren = Zeile löschen (kein `boolean`, sonst gäbe es den dritten Zustand „Zeile da, aber false"). Nur SELECT-Policies, geschrieben wird über `set_cluster_game_access` / `set_cluster_season_access` (beide verlangen `is_any_admin()` **zusätzlich** zur Kurs-Auflösung — `board_target_cluster` allein lieferte einem Schüler brav seinen eigenen Kurs). Der Kurs-Auflöser aus 0062 wird wiederverwendet und nicht kopiert; sein `board_`-Präfix ist seither historisch.

**Sperren löscht nichts** — `game_state`, Kreaturen, Wachstum, Münzen und Highscores bleiben unangetastet, das Spiel ist nur nicht startbar. Auf der Schüler-Kachel steht deshalb bei vorhandenem Monster „Dein Monster wartet hier auf dich."; ohne die Zeile liest sich das Schloss wie ein Verlust. **Der Serverriegel ist absichtlich flach:** `submit_game_result` bleibt offen, damit eine Runde, die beim Zusperren gerade lief, nicht verlorengeht. Geriegelt sind nur die Bonbons (0071).

**Verteilung:** die Schüler-Tablets pollen die Liste alle 20 s (plus sofort bei `visibilitychange`) und zeichnen **nur bei geänderter Liste** neu — sonst zuckte alle 20 Sekunden der halbe Hub. **Admins** hängen in keinem Kurs (Beobachter-Rolle, 0053) und wählen ihn im Hub (`#hubAdminBar`, `sessionStorage` — auf einem geteilten Lehrer-Tablet soll die Wahl mit dem Tab verschwinden, wie im Reality-Check-Board). Für sie zieht auch die Season-Sichtbarkeit am gewählten Kurs (`getEffectiveSeason()`), sonst wäre der Hub für die Lehrkraft leer (Admin = Season 0). Die Kachel zeigt ihnen, was der Kurs **nach** dem Freischalten sähe (`getGameAccessIfOpen()`), plus den Schalter — die Sperre gilt der Klasse, nicht der Lehrkraft. Zum Vorbereiten gibt es dieselbe Matrix im Admin-Panel (Cluster-Tab → „Spiele").

**Die Einhornkatze eröffnet das Bonbon-Prinzip (0071):** `game16` ist ebenfalls sperrbar, und solange sie zu ist, entstehen im **ganzen Kurs** keine Bonbons — vorher sammelt niemand unbemerkt auf ein Ziel hin, das noch gar nicht erklärt wurde. Das Tor steht in `add_bonbons` (zentral, deckt damit auch `board_claim_reward` ab), in `get_cluster_bonbon_status` (`enabled`, daran hängen die +20-Tageshinweise **aller** Kacheln) und in `award_game_bonbons`. ⚠️ Dort **vor** dem `bonbon_daily_claims`-Schreibzugriff: die Funktion setzt den Tagesmarker, bevor sie an `add_bonbons` delegiert — läge das Tor nur dort, wäre der +20-Bonus verbrannt, ohne dass ein Bonbon geflossen ist. Nicht betroffen: die Münzen aus `board_claim_reward` gehen direkt in `game_state.coins`, Reality Check gibt bei gesperrter Einhornkatze also weiter Wachstum und Münzen, nur keine Bonbons.

**Nicht jedes Spiel gehört dem Schalter (Migration 0072):** `games.cluster_managed` — Default `true`, `false` nur für `game1337`. Das Easter-Egg steht in `games`, aber nicht in `GAMES_CONFIG`; es erschließt sich über die Atari-Zahlenreihe, nicht über eine Ansage der Lehrkraft, und ein Schalter, der ein Rätsel aufschließt, nimmt dem Rätsel den Sinn. Das Merkmal steht am Spiel und nicht als ID-Liste in drei Lesestellen, damit ein zweites Easter-Egg später keine Code-Änderung braucht. Wirkung: `set_cluster_game_access` antwortet `not_manageable`, `set_cluster_season_access` überspringt es in **beiden** Zweigen (auf wie zu), `is_game_open_for_cluster` liefert `true` (nicht vom Kurs gesperrt — die Zugangsfrage beantwortet das Rätsel), und `ensureGamesBySeason()` in `admin/app.js` filtert per `cluster_managed=eq.true`, damit es keine Liste gibt, in der es doch wieder auftaucht. **Migration 0073** zieht die **Cluster-Starthilfe** nach: `apply_cluster_bonus` (Neuauflage auf Basis 0053) liest `cluster_managed` mit. Vorher lief die Spiele-Schleife über `select id from games where season = … and active` und legte damit für jeden Season-1-User auch ein Baby-Monster in `game_state['game1337']` — im Hub unsichtbar (die Kachel existiert nicht), aber in der Monster-Rangliste mitgezählt. Die Migration löscht die schon verteilten Phantom-Zeilen, abgesichert über vier Nullbedingungen (`points`/`rounds_played`/`growth`/`coins` = 0): `1337.html` schreibt ausschließlich in den Shop-Blob und ruft nie `saveGameData('game1337')`, ein solcher `game_state` kann also nur aus der Starthilfe stammen — die Bedingungen stehen für den Fall, dass diese Annahme irgendwann fällt. `user_unlocked_games` wird nicht aufgeräumt: seit 0070 bedeutungslos, aber harmlos und der Beleg, wo die Starthilfe schon lief.

**Backfill (0070):** Grundzustand ist „alles zu", also öffnet die Migration für jeden Kurs jedes Spiel, das dort nachweislich schon läuft (`game_state` ∪ `user_unlocked_games`) — genau dafür bleiben `user_unlocked_games` und `unlock_game` stehen und werden nicht gedroppt. `game16` bleibt dabei bewusst zu, **außer** wo das Sammeln schon läuft (Legi vergeben oder Bonbons > 0); einem laufenden Kurs die Sammlung stillzulegen wäre nirgends erklärbar.

**Wortwolken als eigene Schicht (`wc_*`, Migration 0075, 2026-08-17):** Zweite kollaborative Kachel, erste in Season 1: **„Warum Tablets?" (`game20`)**, Ordner `GameHub/S1 wieso weshalb warum/`. Eine Frage — „Warum wollt ihr ein Tablet in der Schule nutzen?" —, zehn Zettel je Kopf (3–60 Zeichen), Zustimmung per Doppeltipp, zwei Phasen (1 Sammeln · 2 Besprechen). Abgeleitet vom Reality Check, aber deutlich kleiner: keine Bereiche, keine Haltungen, keine Themen, keine Recherchen, kein Wachstum.

*Warum eigene Tabellen und nicht `board_*` erweitern:* eine Wortwolke braucht von den sechs Achsen des Reality Check keine. Hätte man sie an `board_notes` gehängt, trüge jeder Zettel Platzhalter für `kind`/`category`/`stance` — Werte, die nie etwas bedeuten und trotzdem in jedem CHECK, jedem Index und jedem RPC mitlaufen; dazu käme ein Primärschlüssel-Umbau an `board_state`/`board_rewards`, während das Board in Kursen offen steht. Stattdessen `wc_state` / `wc_notes` / `wc_likes` / `wc_rewards`, **von Anfang an mit `board_key`**: der Schlüssel IST die Spiel-ID und wird gegen `games` geprüft (`wc_valid_board`), womit auch das Season-Gate am richtigen Spiel hängt, ohne dass eine ID im Funktionsrumpf steht. Eine zweite einfache Wortwolke ist damit eine Kopie des Ordners mit einem anderen `BOARD` in `js/api.js` — keine Migration. Wiederverwendet statt kopiert: `board_target_cluster()` aus 0062 und `is_any_admin()`. RPCs: `wc_get` / `wc_upsert_note` / `wc_delete_note` / `wc_toggle_like` / `wc_set_phase` / `wc_reset` / `wc_claim_reward`; Tabellen haben nur SELECT-Policies. Poll und Signatur-Diff wie beim Board (5 s).

*Phase 2 friert mehr ein als beim Reality Check:* dort bleiben Post-Its in Phase 2 änderbar, weil dort noch gearbeitet wird. Hier ist Phase 2 reines Besprechen — kein Anlegen, kein Ändern, kein Löschen (`phase_locked`). **Zustimmen** geht weiter, in beiden Phasen: das Einfrieren gilt dem Inhalt, nicht dem Gespräch (dieselbe Überlegung wie 0063).

*Belohnung:* **ein** Moment statt zwei — Sammelphase zum ersten Mal beendet (`phase_max >= 2`) ⇒ das Ei schlüpft. **Jeder im Kurs bekommt dasselbe**: Schnecke oder Fisch (50/50, kein Rarity-Roll — wenn beim Nachbarn im ersten Monster-Moment einer Schulung etwas Glitzerndes schlüpft und bei einem selbst nicht, ist der gemeinsame Moment kaputt) und 10 Münzen. Kein Wachstum, **keine Bonbons** (das Bonbon-System gehört der Season 3, 0071 — eine Season-1-Kachel macht dafür keine neue Quelle auf). Die Sequenz läuft in der Kachel selbst (`runReveal()` in `js/wordcloud.js`), nachgereicht wird sie über `syncWordcloud()` in `creatures.js` → `window.__wcReveal` → `maybeShowWordcloudReveal()`. **Seit 0076** würfelt `wc_creature(p_board)` nicht mehr selbst, sondern liest `games.starter_pool` (`{snail, fish}`) — aus derselben Quelle wie die Cluster-Starthilfe, die für game20 damit ebenfalls nur noch Schnecke oder Fisch legt. Liegt beim Schlüpfen schon ein Monster im Spiel, fällt die Vergabe aus, **inklusive der 10 Münzen** (siehe „Das Startmonster gewinnt").

*Drei Sequenzen teilen sich ein Overlay:* `runRevealSequence(spec)` hat dafür ein optionales **`spec.onDone`** bekommen, und `renderHub` ruft statt `if (!A()) B()` jetzt `runPendingReveals()` — eine Warteschlange über Startup Story, Reality Check und Wortwolke. Vorher fiel die zweite wartende Sequenz unter den Tisch, und weil jeder RPC seine Belohnung genau einmal ausgibt, wäre sie damit endgültig weg gewesen.

*Sechs Zettelfarben statt drei Haltungsfarben (`NOTE_RAMPS`/`rampFor` in `js/wordcloud.js`):* die Farbe sagt hier **nichts** aus, sie gliedert nur — Grün, Rosa, Gelb (aus `board.js` übernommen) plus Blau, Lila, Pfirsich, alle in derselben Helligkeit und Sättigung, sonst wäre die Wolke ein Farbkasten. Die drei Zustimmungs-Kanäle bleiben vollständig: Größe, **Sättigung innerhalb des Farbtons** und Stapel, alle drei an der einen Zahl aus `strength()`. Welche Karte welche Farbe bekommt, steht **nicht in der DB**, sondern wird aus der Notiz-ID gerechnet — dadurch auf jedem Gerät dieselbe. Eigener Hash-Faktor (131 statt 31), weil `TILTS` und `NOTE_RAMPS` beide sechs Einträge haben und derselbe Streuwert jeden grünen Zettel in denselben Winkel gelegt hätte. Und anders als die Neigung geht die Farbe **nicht** in den `⟳`-Mischzähler ein: wer „den blauen da oben" sagt, soll ihn nach dem Neuanordnen wiederfinden.

*Unverändert übernommen* ist der ganze Wolken-Apparat (Spirale mit Kollisionsprüfung, virtuelle Tafel, Lupe, Gesten, `dataset.placed`, `TILTS` im Skript, `CLOUD_GAP = 17` + `SHEET_REACH_X/Y`) — wer dort etwas repariert, sollte beide Dateien anfassen. Die CSS-Klassen heißen deshalb auch in `css/wc.css` weiter `bd-`.

**Noch offen:** PDF-Storage-Anbindung. Season 3 (Kreaturen + Games). Diverse UI-ToDos: FokusFlow-Max-Score, Algorithm-Balancing, Theme in DB.

## MPSkills — zweiter Anwendungsbereich

Sammelseite aus Tools/Spielen für den **normalen Unterricht**, losgelöst von der Schulung: Lehrkräfte schalten ein Tool für eine Klasse frei und bekommen einen 6-stelligen Code samt QR, SuS brauchen **keinen Account**. Eigene Landingpage `/MPSkills/`, eigene Optik, nur ein kleiner Link zurück zur Schulung. Referenzdokument: **`Konzept_MPSkills_v1.html`** im Repo-Root (Rollen, Flows, Wireframes, Grenzen, Stufenplan 0–7). Geteilt werden Supabase-Projekt, `auth`, `profiles` und `session.js` — sonst möglichst nichts.

**Aktueller Stand: Stufe 1 (Rolle) umgesetzt, Migration 0077.** Räume, Tools, Codes und anonyme Teilnehmer kommen in Stufe 2–4.

**Die Trennlinie ist die wichtigste Regel des Bereichs:** Auf der Schulungsseite darf man nicht merken, dass MPSkills existiert. Eine freigeschaltete Lehrkraft ist im GameHub ein gewöhnlicher User — pending oder im Kurs, ohne Sonderrechte, ohne zusätzliche Kachel. Deshalb ist die Rolle ein **eigenes Feld** und keine Erweiterung von `is_admin`: dieses Flag öffnet im Hub das Season-Gate, macht Kurs-Sperren sichtbar und schaltet das Admin-Panel frei.

**Rolle (Migration 0077):** `profiles.teacher_status` (`none`/`pending`/`approved`/`rejected`) plus `teacher_requested_at`/`teacher_decided_at`/`teacher_decided_by`, **orthogonal** zu `status` und `cluster_id` — beides kann gleichzeitig gelten. `can_teach()` = `is_admin or is_superadmin or teacher_status='approved'`; Admins sind implizit Lehrkräfte, weil sie jedes Tool testen müssen, ohne sich selbst freizuschalten. Der GameHub liest das Feld nirgends; `user_session` führt es am Ende mit (Reihenfolge der 0053-Spalten unverändert — `create or replace view` lässt kein Umordnen zu).

**Zwei Wege zur Rolle.** Neuanmeldung über MPSkills: `/api/signup` mit `context:'mpskills'` — derselbe Endpunkt wie die Schulung (Namensregeln, Blacklist, Passwort-Policy, Rate-Limit, Rollback sind identisch; ein zweiter Endpunkt wäre eine Kopie mit zwei geänderten Zeilen). Der `context` schaltet genau zwei Dinge: die Cluster-Suche entfällt **komplett** und `teacher_status` startet auf `pending`. Ein unbekannter `context` wird mit `context_invalid` abgewiesen und nicht stillschweigend auf `'schulung'` gedreht — sonst setzte ein Frontend-Tippfehler eine Lehrkraft in den nächsten offenen Kurs, und das fiele erst auf, wenn sie im Hub Monster sammelt. Zweiter Weg für bestehende Schulungs-Accounts: RPC **`request_teacher_role()`** (`none`/`rejected` → `pending`, security definer). Nötig, weil es bewusst **keine** Policy gibt, die einen User sein eigenes Profil schreiben lässt — `profiles_admin_update` ist die einzige UPDATE-Policy (0002/0053).

**Zeitstempel per Trigger, nicht per Client:** `profiles_teacher_stamp_trg` (BEFORE INSERT OR UPDATE, erster Trigger auf `profiles`) setzt die drei Stempel selbst und ist ein No-Op, solange sich `teacher_status` nicht ändert — `profiles` ist die heißeste Tabelle im System. Grund: freigeschaltet wird per **PATCH auf `profiles`** aus dem Admin-Panel (wie Cluster-Zuweisung und `display_name_locked`, gedeckt durch `profiles_admin_update`), und damit könnte der Browser `teacher_decided_by` frei mitschicken und die Entscheidung einem anderen Admin zuschreiben. Im service_role-Kontext (Signup) ist `auth.uid()` null → `decided_by` bleibt leer, was richtig ist: dort hat niemand entschieden, dort wurde beantragt.

**Admin-Panel → Tab „Lehrkräfte"** (`admin/app.js`, `renderTeachers`): Filter Status/Suche, Aktionen Freischalten · Ablehnen · Rolle entziehen · Antrag entfernen. Sichtbar für **Schul- und Volladmin**; der Schul-Scope kommt aus `profiles_select_own` (0053), es wird hier nichts zusätzlich gefiltert. Die Liste zeigt nur `teacher_status <> 'none'` (alle anderen stehen im User-Tab), sortiert nach ältestem Antrag. Zwei Spalten mit Absicht nebeneinander: **MPSkills** und **Schulung** — damit sichtbar bleibt, dass eine freigeschaltete Lehrkraft dort weiter `pending` ist. Die Schul-Spalte erscheint nur für Volladmins; für einen Schuladmin stünde in jeder Zeile derselbe Wert (und `allSchools` ist für ihn leer, siehe `initSchoolSwitcher`). Nur „Rolle entziehen" fragt nach — es ist der einzige Schritt, der jemandem etwas wegnimmt, das er schon benutzt.

**Frontend Stufe 1:** `MPSkills/index.html` + `app.js` + `style.css`. Die Optik ist bewusst **nicht** das Fantasy-Kleid (Cinzel/Gold auf Braun), sondern Werkzeugkasten: heller Grund, Tinte, **ein** Akzent (Teal `#0f766e`), Warnrot nur für Fehler — die Farbwerte stammen aus der Konzeptseite, und hell deshalb, weil die Seite an den Beamer geht. `session.js` wird unverändert mit demselben `storageKey` wiederverwendet: ein Konto, zwei Bereiche, eine Anmeldung. Die ganze Seite ist eine **Rollenweiche** (`roleOf()` → `guest`/`admin`/`teacher`/`pending`/`rejected`/`noRole`), an der ab Stufe 2 die Tool-Kacheln hängen. **Noch nicht von der Schulungs-Landing verlinkt** — der Link kommt in Stufe 2, solange ist die Seite nur per URL erreichbar (`noindex`).

**Was in Stufe 3 mitgelöst werden muss:** `window.__accessToken` veraltet nach `TOKEN_REFRESHED` (`session.js` kehrt bei dem Event früh zurück). Im Admin-Panel ist das ein F5 wert; die Beamer-Ansicht einer Lehrkraft steht aber 90 Minuten offen und der Refresh kommt nach 60. Betrifft in Stufe 1 nur `request_teacher_role()`, das direkt nach dem Anmelden aufgerufen wird.

## Architecture

The landing page (`index.html`) is a standalone HTML file — no shared JS or CSS with GameHub. It links to `GameHub/index.html` and PDF files in `Dokumente/`.

GameHub uses a hub-and-spoke model: `GameHub/index.html` is the central hub, each game lives in its own folder, and `creatures.js` is the only shared JS between hub and games. See `GameHub/CLAUDE.md` for the full data flow, game-adding guide, creature logic, and localStorage state shape.

### Game Access Control

Fünf Zustände in `getGameAccess()` (`GameHub/script.js`): `available` · `locked` (Season-Gate oder Not-Aus) · `admin_locked` (Kurs-Sperre) · `cluster_locked` / `ready_to_reveal` (Einhornkatze). `config.js` ist seit Migration 0070 **nur noch der Not-Aus** (`status: 'locked'` schaltet ein Spiel global ab) — wer ein Spiel freischaltet, steht in `cluster_unlocked_games`. Siehe „Kurs-Freischaltung" oben.

### Shop & Coin Economy (in `script.js`)

The hub has an in-game shop where students spend coins to buy growth potions, additional egg slots, and the creature codex ("Buch der Monster"). Coins and shop inventory are stored in the same `lernwelt_v3` localStorage key alongside game state.

### Creature Rarity Tiers

Beyond the 7 base creature types (Schnecke → Drache), creatures can have **Rare / Epic / Legendary** status applied via CSS animated overlays (glitter effects). Rarity is tracked in localStorage and displayed in the gallery modal.

### `S2 The Algorithm` — Complex Subgame

This is the most architecturally complex game: a smartphone-addiction simulation with its own module system (`GameHub/S2 The Algorithm/js/`), separate `CLAUDE.md`, and game design document (`The_Algorithm_GDD.md`). It models Dopamin, Balance, Reizsättigung, and Sozialerdrang as resource bars driven by a card-based feed system. Real time (8 min) maps to in-game time (15:00–03:00).
