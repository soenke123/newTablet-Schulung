Zweiter Anwendungsbereich

MPSkills — Werkzeuge und Spiele für den Unterricht, losgelöst von der Schulung

Eine eigene Sammelseite: Lehrkräfte schalten ein Tool für eine Klasse frei und bekommen dafür einen Code samt QR. Schüler brauchen keinen Account — Code scannen, drin sein, mitmachen. Nach 60 Tagen Ruhe räumt sich der Raum selbst weg.

01 Die Idee

Die Plattform kann heute genau eine Sache: eine Schulungs-Kohorte durch eine Season aus Spielen führen. Alles hängt daran — Season-Gate, Kurs-Freischaltung, Kreaturen, Bonbons. MPSkills ist das Gegenstück: einzelne Dinge, die im normalen Unterricht sofort nützlich sind, ohne Kohorte, ohne Season, ohne Sammelfortschritt.

🧰 Sammelstelle statt Kurs

Kein Lehrpfad, keine Reihenfolge. Jedes Tool steht für sich und wird einzeln benutzt.

🔑 Lehrkraft schaltet frei

Ohne Raum passiert nichts. Die Lehrkraft entscheidet, was ihre Klasse wann öffnen kann.

📱 Schüler ohne Account

QR scannen genügt. Kein Name, kein Passwort, keine Anmeldung — sofern die Lehrkraft es so will.

🕓 Räume verfallen

60 Tage nach der letzten Aktivität ist der Raum weg. Keine Altlasten, kein Aufräumdienst.

Der Satz, an dem am Ende gemessen wird: Eine Lehrkraft öffnet für ihre 9b einen Raum, zeigt den QR-Code am Beamer, und 28 Tablets sind in 30 Sekunden drin — ohne dass ein einziges Passwort im Raum gesagt wurde.

02 Abgrenzung zur Tablet-Schulung

Beide Seiten teilen Datenbank, Auth und Deployment — und sonst möglichst nichts. Die Trennlinie muss scharf sein, sonst wandern Season-Logik und Kreaturen langsam in die neue Seite hinein.

Harte Regel: Auf der Schulungsseite darf man nicht merken, dass MPSkills existiert. Eine freigeschaltete Lehrkraft ist im GameHub ein gewöhnlicher User — pending oder im Kurs, ohne Sonderrechte, ohne zusätzliche Kachel, ohne veränderte Anzeige. Deshalb ist die Lehrkraft-Rolle ein eigenes Feld und nicht eine Erweiterung von is_admin.

Der Weg zur Lehrkraft-Rolle

Anmeldung über MPSkills ┌──────────────────────────────────────────────┐ │ profiles.teacher_status = 'pending' │ │ profiles.cluster_id = NULL ← immer │ │ profiles.status = 'pending' │ └──────────────────────────────────────────────┘ │ ▼ Admin-Panel → Tab „Lehrkräfte" ┌──────────────────────────────────────────────┐ │ [ Freischalten ] → teacher_status=approved │ │ [ Ablehnen ] → teacher_status=rejected │ └──────────────────────────────────────────────┘

Wichtig: die Anmeldung über MPSkills weist nie einen Kurs zu — auch dann nicht, wenn gerade ein Kurs-Zeitfenster offen steht. Auf der Schulungsseite ist die Lehrkraft damit ein pending-User wie jeder andere und kann später ganz normal einem Kurs beitreten.

04 Weg der Lehrkraft

Von der Anmeldung bis zum Beamer — fünf Schritte, davon vier einmalig.

1

Anmelden

Schule wählen, Accountname, Anzeigename (das Kürzel, das die Klasse kennt), Passwort. Danach: „Deine Freischaltung als Lehrkraft ist beantragt."

2

Freigeschaltet werden

Ein Schul- oder Volladmin bestätigt im Admin-Panel. Ab dann sieht die Lehrkraft alle Tools.

3

Ausprobieren

„Testen" auf einer Tool-Kachel öffnet einen Testraum — ein normaler Raum, nur als Test markiert. Es gibt bewusst keinen Solo-Modus: jedes Tool hat genau einen Code-Pfad, damit der Test das echte Verhalten zeigt.

4

Raum für die Klasse anlegen

Titel („9b Deutsch"), Namen abfragen ja/nein, tool-eigene Einstellungen (bei der Wortwolke: die Frage). Ergebnis ist ein Code wie K7F2QM plus QR.

5

Beamen und moderieren

Beamer-Ansicht zeigt QR und Code groß. Daneben: wer ist drin, Beitritt öffnen/schließen, Beitrag ausblenden, Tablet sperren, Phase weiterschalten.

Mehrere Klassen, mehrere Räume. Dasselbe Tool kann beliebig oft aufgemacht werden — 9b und 9c bekommen getrennte Räume mit getrennten Codes und getrennten Inhalten. In der Raumliste der Lehrkraft stehen sie mit Titel und Restlaufzeit nebeneinander.

05 Weg der Schüler

Der Normalweg ist der QR-Code. Der Code zum Tippen ist der Rückfallweg für Geräte ohne Kamera und für die, bei denen das Scannen nicht klappt.

QR scannen (Normalweg) Kamera → …/MPSkills/j.html#K7F2QM │ ▼ ┌────────────────────────────┐ │ 9b Deutsch │ │ Wortwolke │ │ │ │ Dein Name │ │ ┌──────────────────────┐ │ │ │ Mia │ │ │ └──────────────────────┘ │ │ [ Mitmachen ] │ └────────────────────────────┘
Code tippen (Rückfallweg) mpskills aufrufen │ ▼ ┌────────────────────────────┐ │ Code von der Tafel │ │ ┌──┬──┬──┬──┬──┬──┐ │ │ │K │7 │F │2 │Q │M │ │ │ └──┴──┴──┴──┴──┴──┘ │ │ [ Weiter ] │ │ │ │ Meine Räume (dieses Gerät) │ │ · 9b Deutsch · Wortwolke │ └────────────────────────────┘

Alphabet ohne Verwechslungsgefahr: 23456789ABCDEFGHJKLMNPQRSTUVWXYZ — kein O/0, kein I/1. Sechs Stellen ergeben gut eine Milliarde Möglichkeiten, Durchprobieren ist damit aussichtslos. Der Code steht im URL-Hash, nicht im Query-String: so landet er nicht in Server-Logs.

Was aus dem Beitritt entsteht

Beitritt → Server legt einen Teilnehmer an → gibt einen geheimen Token zurück localStorage['mpskills_rooms'] = [ { code:'K7F2QM', token:'c1f9…8a3', room:'9b Deutsch', tool:'wordcloud' }, { code:'PQ4H7T', token:'77b2…e10', room:'Abstimmung', tool:'poll' } ] Jeder weitere Aufruf schickt nur den Token. Der Server löst daraus Teilnehmer + Raum auf — die Seite selbst nennt nie eine Raum-ID.

Ohne Account

Die Token-Liste liegt im Gerät. Auf einem Klassensatz-Tablet ist genau das der Sinn: der Raum von gestern ist morgen noch da.

Mit Account

Ist ein Schüler eingeloggt, hängt der Teilnehmer zusätzlich an seiner User-ID — dann findet er seine Räume auch auf einem anderen Gerät wieder.

Anonymer Raum

Hat die Lehrkraft „Namen abfragen" ausgeschaltet, entfällt das Namensfeld und jeder heißt intern Tablet 1…n.

06 Der Raum

Der Raum ist die zentrale Einheit: er verbindet ein Tool, eine Lehrkraft und eine Gruppe von Teilnehmern — und er hat ein Ablaufdatum.

Raum K7F2QM · „9b Deutsch" ├─ Tool wordcloud ├─ Besitzerin Lehrkraft (Account) ├─ Schule MPS ├─ Namen abfragen ●○ anonym ├─ Beitritt offen ●○ zu ├─ Einstellungen { question: "Warum wollt ihr …?" } ├─ Zustand { phase: 1 } ← Lehrkraft steuert ├─ Teilnehmer Mia · Ben · Ayla · … (Token je Gerät) ├─ Beiträge Zettel, Antworten, Stimmen └─ läuft ab letzte Aktivität + 60 Tage

Lebenszyklus

anlegen ──► benutzen ──────────────► 60 Tage Ruhe ──► weg │ ▲ ▲ │ └── jede Aktivität setzt │ │ die Frist zurück │ ├──► [ Verlängern ] ───────────────────┘ ├──► [ Beitritt zu ] Raum lesbar, niemand kommt neu dazu └──► [ Löschen ] sofort weg, mit Rückfrage

Frist ab letzter Aktivität

Nicht ab dem Anlegen. Ein Raum, der über Wochen weiterbenutzt wird, verfällt nicht mitten in der Reihe.

Aufgeräumt wird zweifach

Beiläufig bei jedem Zugriff der Lehrkraft, zusätzlich einmal täglich automatisch — damit auch Räume verschwinden, die niemand mehr anfasst.

Löschen heißt löschen

Raum, Teilnehmer, Beiträge, Stimmen — alles. Die Token der Schüler laufen dann in eine klare Meldung, nicht in einen Fehler.

Grenzen

GrenzeWertWie gezählt wird
Teilnehmer je Raum 60 Jedes Gerät ist ein Teilnehmer. Wer den Browser-Speicher löscht und neu beitritt, belegt einen zweiten Platz — bei einem Klassensatz von 30 ist die Luft dafür da. Ist der Raum voll, sagt der Beitritt das klar („Dieser Raum ist voll"), statt einen Fehler zu zeigen.
Räume je Tool und Lehrkraft 5 Gezählt werden nur lebende Räume. Abgelaufene zählen nicht mehr mit, der Testraum ebenfalls nicht. Ist die Grenze erreicht, zeigt die Raumliste, welcher Raum am längsten unbenutzt ist, mit einem Löschen-Knopf daneben.
Beiträge je Teilnehmer je Tool Steht als Grenze in der Registry (bei der Wortwolke: 10 Zettel, 3–60 Zeichen), nicht global.

Ein Vorbehalt zu den 5 Räumen je Tool. Eine Deutschlehrkraft mit fünf Klassen sitzt damit genau auf der Grenze — kommt eine Vertretung oder ein zweiter Kurs dazu, muss sie erst einen Raum löschen. Weil die Frist erst nach 60 Tagen Ruhe greift, räumt sich das nicht rechtzeitig von selbst auf. Die Grenze bleibt bei 5, aber sie steht als eine Zahl an einer Stelle: fällt im Betrieb auf, dass sie zu eng ist, ist das eine Zeile und keine Umbaumaßnahme.

07 Datenmodell

Ein neues Feld am Profil, sieben neue Tabellen — alle mit Präfix skill_, damit auf einen Blick klar ist, was zu MPSkills gehört und was zur Schulung.

Am bestehenden Profil

profiles + teacher_status 'none' | 'pending' | 'approved' | 'rejected' + teacher_requested_at / teacher_decided_at / teacher_decided_by

Bewusst orthogonal zu status und cluster_id: eine freigeschaltete Lehrkraft kann gleichzeitig Teilnehmerin einer Schulung sein. Die Schulungsseite liest das Feld nirgends.

Neue Tabellen

TabelleWofürBesonderheit
skill_tools Registry der Tools: Titel, Ordner, Icon, Grenzen Spiegel von MPSkills/tools.js — wie games ↔ GAMES_CONFIG
skill_rooms der Raum: Code, Tool, Besitzerin, Titel, Einstellungen, Ablaufdatum expires_at ist eine echte Spalte — sonst gäbe es kein „Verlängern"
skill_participants ein Gerät bzw. eine Person im Raum trägt den Token — das einzige Geheimnis der Schülerseite
skill_room_state was die Lehrkraft steuert (Phase, aktuelle Frage) ein jsonb je Raum, vom Tool interpretiert
skill_room_entries Beiträge: Zettel, Antworten, Ergebnisse payload jsonb + hidden für Moderation
skill_room_votes Zustimmung zu einem Beitrag Primärschlüssel erledigt „genau eine Stimme" — kein Zähler, der doppelt läuft
skill_join_attempts Protokoll für das Beitritts-Rate-Limit gleiches Muster wie signup_attempts

Warum eine generische Schicht statt Tabellen je Tool. Die Schulung hat für ihre kollaborativen Kacheln eigene Schemata (board_*, wc_*), weil dort jede Achse eine Bedeutung trägt. MPSkills ist das Gegenteil: eine Sammlung, die wachsen soll. Deshalb ein Satz Tabellen für alle — ein neues Tool ist ein Ordner und eine Zeile in der Registry, keine Migration. Der Preis: die Gültigkeitsprüfung (Länge, Anzahl, erlaubte Felder) steht als jsonb in der Registry und nicht als Constraint an der Spalte. Für ein Tool, das wirklich mehr braucht — eine Simulation, ein Buzzer auf Millisekunden — bleibt der Weg zu eigenen Tabellen offen.

08 Sicherheitsmodell

Das ist die neuralgische Stelle des ganzen Vorhabens. Bisher lag unter jedem Zugriff ein Sicherheitsnetz: die Datenbank prüft selbst, wem eine Zeile gehört. Für Teilnehmer ohne Account gibt es dieses Netz nicht — sie sprechen als anonyme Rolle mit dem Server.

Kein direkter Tabellenzugriff für Anonyme. Die anonyme Rolle darf ausschließlich eine Handvoll benannter Server-Funktionen aufrufen — kein Lesen, kein Schreiben an einer Tabelle, nicht einmal lesend. Das Muster ist etabliert (bei Reality Check und der Wortwolke wird schon ausschließlich über Funktionen geschrieben), hier gilt es zusätzlich fürs Lesen.

Keine Funktion nimmt eine Raum- oder Teilnehmer-ID von außen. Die erste Zeile jeder anonymen Funktion löst den Token auf; alle weiteren IDs stammen aus dieser Auflösung. Sonst könnte ein Teilnehmer mit gültigem Token in einen fremden Raum schreiben.

Der Token verlässt die Datenbank genau einmal — in der Antwort auf den Beitritt. In keiner Liste, keiner Ansicht, keiner Aktualisierung tauchen die Token anderer Teilnehmer auf.

Warum der Beitritt über den Server läuft und nicht über die Datenbank

Der Raum-Code ist das einzige erratbare Geheimnis im System. Wer ihn prüft, sollte auch zählen können, wie oft jemand daneben liegt — und die Client-Adresse sieht nur die Server-Funktion, nicht die Datenbank. Der Beitritt bekommt deshalb einen eigenen Endpunkt, genau wie die Anmeldung: Code prüfen, Raum offen?, Schimpfwort-Prüfung auf den Namen (dieselbe Liste, die schon bei der Anmeldung greift), Teilnehmer anlegen, Token zurückgeben. Alles danach läuft direkt gegen die Datenbank-Funktionen.

Aktualisierung: zwei Anfragen statt einer

alle 3 s Signatur? → "27 Beiträge, Stand 14:32:07, Phase 1" ← billig │ nur wenn geändert ▼ vollständige Ansicht → Raum, Zustand, Beiträge, Stimmen ← teuer

28 Tablets × alle 3 Sekunden × mehrere Klassen gleichzeitig — das ist der Unterschied zwischen einer teuren und einer billigen Anfrage pro Tablet. Deshalb steckt die Trennung von Anfang an drin und wird nicht nachgerüstet.

10 Was ein Tool ist

Damit die Sammlung wachsen kann, muss „ein Tool hinzufügen" klein bleiben. Deshalb ist festgelegt, was ein Tool vom System bekommt — und was es selbst mitbringen muss.

Das System stellt

Raum, Code, QR, Beitritt, Teilnehmerliste, Aktualisierung, Zustand der Lehrkraft, Beiträge, Zustimmung, Moderation, Ablauf.

Das Tool bringt

Einen Ordner mit Darstellung und Bedienung, eine Zeile in der Registry, und die Bedeutung dessen, was in payload steht.

Erstes Tool: Wortwolke

Die Engine aus „Warum Tablets?" wird portiert — Spirale, virtuelle Tafel, Lupe, Gesten bleiben unangetastet. Neu ist nur die Datenanbindung.

Warum die Wortwolke als erstes Tool. Sie ist die einzige Sache in dieser Kette, die schon erprobt ist. Wenn beim ersten Klassentest etwas nicht stimmt, liegt es dann mit hoher Wahrscheinlichkeit am neuen Fundament — Raum, Token, Aktualisierung — und nicht am Tool. Ein neu gebautes Tool hätte diese Aussagekraft nicht.

Weg fallen dabei: Kreatur-Belohnung, Wachstum, Münzen, Season-Gate, Kurs-Bezug. Die Frage tippt die Lehrkraft beim Anlegen selbst ein, statt dass sie fest im Spiel steht.

Kandidaten danach

  • Abstimmung — Frage plus Optionen, Balken live. Beweist, dass die Registry trägt (Ordner + eine Zeile, keine Migration).
  • Gruppen-Auslosung / Zufallsrad — braucht nur die Teilnehmerliste, keine Beiträge.
  • Kartenabfrage — jeder schreibt drei Begriffe, die Lehrkraft sortiert sie am Beamer in Gruppen.
  • Buzzer / Quiz — der erste Kandidat, der die generische Schicht sprengen könnte; deshalb bewusst nicht als zweites Tool.

12 Risiken — und wo es weh tut

Machbar ist das Ganze, weil fast alles auf Bekanntem aufsetzt: Anmeldung, Schul-Rollen, Admin-Panel, das Funktions-Muster der Datenbank, die Aktualisierung per Abfrage, und mit der Wortwolke ein fertiges kollaboratives Tool. Genau eine Sache ist wirklich neu: Teilnehmer ohne Account. Alles andere ist Variation.

Was jetzt, was später

Die meisten Punkte hier sind Arbeit, die man aufschieben kann. Zwei sind es nicht — nicht weil sie dringend wären, sondern weil sie keine Aufgaben sind, sondern Eigenschaften der Bauweise. Sie kosten beim Bauen nichts und beim Nachrüsten viel.

PunktWannWarum
Kein Sicherheitsnetz (Regel „keine ID von außen") beim Bauen Keine Aufgabe, sondern eine Regel beim Schreiben jeder Funktion. Nachträglich heißt es: jede Funktion einzeln prüfen — und die eine übersehene ist genau das Leck.
Signatur getrennt von Ansicht beim Bauen Kostet in Stufe 3 eine zusätzliche kleine Funktion. Nachträglich hängt jedes bereits gebaute Tool an der alten Abfrage und muss mit umgestellt werden.
Token-Erneuerung in der Beamer-Sitzung Stufe 3 Kleiner, örtlich begrenzter Fix. Aber vor dem ersten echten Klasseneinsatz, sonst steht die Lehrkraft nach 60 Minuten vor einer toten Seite.
Moderation, Schimpfwortprüfung, Beitritt sperren Stufe 5 Ohnehin später eingeplant. Grenze ist nicht die Stufe, sondern der erste Einsatz mit einer echten Klasse — vorher reicht der Testraum.
Datenschutz-Absatz Stufe 7 Die zwei Mechanismen, auf die er sich beruft (60 Tage, anonymer Raum), sind von Anfang an drin. Es fehlt nur der Text.
Tools, die nicht in die generische Schicht passen je Tool Nichts zu beheben, solange kein solches Tool ansteht. Entschieden wird das dann am konkreten Tool.
Aufwandsschwerpunkt · zwei Landingpages — Keine Fehler, sondern Dinge, die man beim Schätzen und beim Verlinken im Kopf behalten muss.

Kein Sicherheitsnetz unter den anonymen Zugriffen

Bisher war eine vergessene Prüfung halb abgefedert, weil die Datenbank selbst noch einmal nachsah, wem eine Zeile gehört. Für Anonyme liegt darunter nichts. Die drei Regeln aus Abschnitt 08 sind deshalb keine Stilfrage — besonders „keine ID von außen".

Die Beamer-Sitzung läuft länger als die Anmeldung gültig ist

Es gibt einen bekannten Fehler: der Zugangsschlüssel der Lehrkraft wird im Hintergrund erneuert, die Seite merkt es aber nicht und arbeitet mit dem alten weiter. Im Admin-Panel kostet das ein F5. Hier trifft es eine Seite, die 90 Minuten offen steht, während die Erneuerung nach 60 Minuten fällig wird — mitten in der Stunde. Muss in Stufe 3 mitgelöst werden.

Anonyme Beiträge in einer Klasse

Kein Account heißt keine Rechenschaft. Schimpfwortprüfung, Ausblenden, Tablet sperren und „Beitritt zu" sind Pflichtausstattung, nicht Politur — deshalb stehen sie in Stufe 5 und nicht in Stufe 7.

Last durch das Aktualisieren

28 Tablets alle 3 Sekunden, mehrere Klassen parallel. Beherrschbar, aber nur mit der Trennung in billige Signatur und teure Ansicht. Ohne sie wird das der Engpass, sobald zwei Klassen gleichzeitig arbeiten.

Tools, die nicht in die generische Schicht passen

Ein Buzzer auf Millisekunden, eine Simulation mit großem Zustand. Für die bleibt der Weg zu eigenen Tabellen offen — aber jedes Tool, das ihn nimmt, kostet wieder eine Migration und damit den Vorteil der Sammelseite.

Datenschutz

Namen von Minderjährigen ohne Account. Die Antwort darauf sind die 60-Tage-Löschung und der „anonym"-Schalter pro Raum; dazu gehört ein kurzer, ehrlicher Absatz auf der Landing. Nichts davon ist technisch schwierig — es darf nur nicht vergessen werden.

Aufwandsschwerpunkt liegt nicht in der Datenbank

Die Migrationen sind überschaubar. Die längste Einzelstufe ist die Lehrer-Seite: Raumverwaltung, Beamer-Darstellung, Moderation. Wer den Aufwand an den Tabellen schätzt, schätzt zu niedrig.

Zwei Landingpages, ein Projekt

Die Gefahr ist nicht technisch, sondern begrifflich: dass die beiden Bereiche zusammenwachsen, weil es bequem ist. Ein Link im Fuß, kein Wechsel-Menü.
